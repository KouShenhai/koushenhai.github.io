MQTT配置

你好呀，我的老朋友！我是老寇，欢迎来到老寇IoT云平台！

平台通过 laokou-common-mqtt 作为 MQTT 5 客户端连接外部 Broker。接入一个网关通常只需在 IoT 服务里配置会话，让网关按约定的 Topic 和二进制格式收发消息。下面用租户 laokouyun、网关 GW001 跑通属性上报，再说明怎样增加一种消息。

# 1. 创建并开启 MQTT 会话

准备一个 IoT 服务可访问的 MQTT 5 TCP 端口。Broker 需要支持共享订阅，平台账号需要有相应 Topic 的订阅和发布权限。使用项目现有的 IoT 服务时，还需启动其数据库、Pulsar 和 Redis，分别用于保存会话、转发消息和缓存属性。

  1. 在平台的「会话管理」中新增一条会话，填写名称、Broker 的 IPv4 地址、端口、用户名和密码。同一租户的主机和端口组合须唯一。服务端保存和修改时都会用 Paho 建立一次测试连接，超时为 10 秒，测试后即断开。
  2. 保存后开启会话。对应 IoT 服务接口为 POST /v1/sessions 和 PUT /v1/sessions/{id}/open。保存接口的请求体见下例，地址和凭据请换成实际值。若经 API 网关调用，使用部署环境的路由前缀及登录凭据。
  3. IoT 服务通过 Pulsar 收到开启事件后，按会话 ID 读取配置，由 MqttClientManager 异步建立 Netty 长连接。看到日志「连接 MQTT Broker 成功」后，在 Broker 上确认该客户端已获准订阅 $share/iot/up/laokouyun/+/properties/report。服务启动时也会加载数据库中 state = 1 的会话。
  4. 在「网关管理」中登记 SN 为 GW001 的网关并关联该会话。下发指令时，平台用关联的 sessionId 选择 Broker 连接。更换地址或凭据时，先关闭会话（PUT /v1/sessions/{id}/close），修改并保存，再重新开启。同一 ID 重复调用 open 会复用原客户端。
{
  "co": {
    "name": "网关联调",
    "host": "192.0.2.10",
    "port": 1883,
    "username": "iot-client",
    "password": "<Broker 密码>",
    "state": 0
  }
}

# 全局配置与单条连接参数

laokou-iot-start/src/main/resources/application.yml 中与本例相关的配置如下。所有会话共享一个 Netty 事件循环组。租户编码同时用于生成 MQTT 订阅和 Pulsar Topic。

system-settings:
  tenant-code: laokouyun
spring:
  mqtt-client:
    core-size: 32

SpringMqttClientProperties 只绑定 core-size，类默认值为 16，IoT 启动模块将其设为 32。每条连接的参数由 SessionConvertor.toProperties 组装。要给单个会话调心跳或 ACK 超时，可在该转换入口设置 MqttClientProperties。若需要在管理页编辑，还需将字段接入会话 DTO、存储和表单。

连接字段 项目取值 生效位置
host、port 会话记录；类默认 127.0.0.1:1883 Netty TCP 连接，当前管线使用明文 MQTT
username、password 会话记录 CONNECT 认证
tenantCode、identifier 系统租户编码、默认随机生成的 16 个字符 Client ID 为转成大写的 tenantCode-identifier
cleanSession true MQTT 5 CONNECT 的 Clean Start 标志
keepAliveTimeSeconds 60 秒 周期性发送 PINGREQ，读空闲达到 1.5 倍心跳间隔时关闭连接并触发重连
connectTimeoutMs 15000 毫秒 Netty 建立 TCP 连接的超时
maxBytesInMessage 67108864 字节（64 MiB） MQTT 入站解码上限
ackTimeoutMs 5000 毫秒 已连接时，出站 QoS 1/2 报文等待确认的重发间隔

在其他业务模块复用时，参照 laokou-iot-infrastructure 引入同版本的 org.laokou:laokou-common-mqtt。参考 IotConfig 将 MqttEventLoop 和 MqttClientManager 注册为带 destroyMethod = "close" 的 Bean，并让 Spring 扫描配置类 SpringMqttClientProperties 和所需的监听器。调用 manager.open(sessionId, properties, mqttEventLoop, listeners) 建连，后续用同一个 ID 发布消息或关闭连接。项目现有的 IoT 服务已经完成这些装配。

# 2. 上报第一条网关属性

在网关侧以独立的 MQTT 客户端连接同一 Broker，向 up/laokouyun/GW001/properties/report 发布，QoS 取 0。发布地址使用具体的租户和 SN；$share/iot/ 是平台订阅时添加的共享组前缀，同组的多个平台实例分担消息。

现有属性监听器把 MQTT payload 原样写入 Pulsar，IoT 消费者再用 MqttForyFactory 解码。网关需发送 Apache Fory 跨语言格式的原始字节。下面的 Java 示例可在引用了 org.laokou:laokou-common-mqtt:${revision} 的独立联调程序中生成载荷。平台端已由 IotConfig 注册类型；独立发送端在首次序列化前注册一次相同的类型编号。

import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Map;
import org.laokou.common.mqtt.client.MqttForyFactory;
import org.laokou.common.mqtt.client.message.UpReportPropertiesGatewayMessage;

public class GatewayReportDemo {
    static void main(String[] args) throws Exception {
        var codec = MqttForyFactory.INSTANCE;
        codec.register(UpReportPropertiesGatewayMessage.class, 244);

        var report = new UpReportPropertiesGatewayMessage();
        report.setTenantCode("laokouyun");
        report.setGatewaySn("GW001");
        report.setTimestamp(System.currentTimeMillis());
        report.setProperties(Map.of("temperature", 23.5));
        Files.write(Path.of("gateway-report.bin"), codec.serialize(report));
    }
}

用支持二进制文件发布的 MQTT 客户端，将 gateway-report.bin 的原始内容作为 payload 发到上述 Topic。使用 Mosquitto 命令行时，可在生成文件的目录执行（替换地址和凭据）。

mosquitto_pub -V mqttv5 -h 192.0.2.10 -p 1883 -u iot-client -P '<Broker 密码>' -t 'up/laokouyun/GW001/properties/report' -q 0 -f gateway-report.bin

可在 Pulsar、Redis 和业务接口分别验证这次上报。

  1. 平台将载荷转发到 persistent://laokouyun/gateway/iot-up-report-properties-gateway-message。
  2. MqttMessageHandler 批量消费后调用 set_properties.lua 更新 Redis。执行 HGETALL gateway:properties:laokouyun:GW001，字段 timestamp 应为上报时间，data 应包含 temperature 值 23.5。重复联调时重新生成文件，脚本只在缓存为空或新时间戳更大时更新。
  3. 用已登记网关的数据库 ID 请求 GET /v1/gateways/{id}/properties，即可从业务接口核对属性。缓存键取自载荷的租户编码和网关 SN，因此应与发布 Topic 及平台网关记录一致。

# 3. 查 Topic、QoS 与载荷类型

下表用 {t}、{g}、{d} 分别表示租户编码、网关 SN 和设备 SN。QoS 是 MqttMessageType 向 Broker 请求的订阅级别。Pulsar 完整地址为 persistent://{t}/{命名空间}/{主题名}。

消息 MQTT 发布 Topic 订阅 QoS Pulsar 命名空间 / 主题名
网关属性 up/{t}/{g}/properties/report 0 gateway/iot-up-report-properties-gateway-message
设备属性 up/{t}/{g}/{d}/properties/report 0 gateway/iot-up-report-properties-device-message
网关指令回复 up/{t}/{g}/command/reply 1 gateway/iot-up-command-reply-gateway-message
设备告警 up/{t}/{g}/{d}/event/alarm 1 device/iot-up-alarm-event-device-message
网关固件信息上报 up/{t}/{g}/ota/report 1 gateway/iot-up-report-ota-gateway-message
固件信息上报回复 up/{t}/{g}/ota/report/reply 1 gateway/iot-down-report-ota-reply-gateway-message
网关固件升级 up/{t}/{g}/ota/upgrade 1 gateway/iot-up-upgrade-ota-gateway-message
固件升级回复 down/{t}/{g}/ota/upgrade/reply 1 gateway/iot-down-upgrade-ota-reply-gateway-message
固件升级进度 up/{t}/{g}/ota/upgrade/process 1 gateway/iot-up-upgrade-ota-process-gateway-message

固件信息上报回复在当前枚举中使用 up/，升级进度的末段拼作 process。设备告警监听器写入 Pulsar 的 device 命名空间，而 DefaultPulsarTopicFactory 会把上述枚举统一建在 gateway 下。接入告警时，要让建主题、发送和消费三处指向同一实际地址。OTA 监听器同样只负责转发载荷，具体升级处理由消费端实现。

网关指令下发走相反方向。网关订阅 down/{t}/{g}/command。例如平台调用 POST /v1/gateways/commands/read-device-properties-command 后，IoT 服务消费内部的 GatewayCommandEvent，转换成 DownCommandGatewayMessage，再调用 mqttClientManager.publish(sessionId, topic, payload, MqttQoS.AT_LEAST_ONCE)。网关解码后执行 command，把同一个 requestId 放入回复，发到 up/{t}/{g}/command/reply。平台用它查找指令记录，以回复的 message 是否等于 "OK" 标记执行结果。联调时同时核对下发状态和回复状态。

MQTT 载荷类 Fory 类型编号 业务字段
UpReportPropertiesGatewayMessage 244 tenantCode、gatewaySn、毫秒 timestamp、properties
UpReportPropertiesDeviceMessage 245 在网关信息外携带 deviceSn、deviceName 和设备 properties
DownCommandGatewayMessage 246 requestId、command、param 及目标网关或设备信息
UpCommandReplyGatewayMessage 247 原 requestId、message、结果 payload 等

两端需要约定相同的字段和编号。MqttForyFactory 开启 withXlang(true)，关闭引用跟踪；平台内部 Pulsar 控制事件另用 ForyFactory。若接入只会发送 JSON 的设备，可新增专用 Topic，在自定义监听器或对应的 Pulsar 消费者中按 JSON 解码。

# 4. 二开示例：增加网关诊断上报

假设要接收 up/laokouyun/GW001/diagnostics/report，让 IoT 服务异步处理诊断数据。需要同时定义 Broker 的订阅、MQTT 到 Pulsar 的转发，以及最终的业务消费者。

  1. 在 org.laokou.common.mqtt.client.message.MqttMessageType 中增加枚举项，沿用现有枚举的四个方法。

    定义 本例取值
    枚举名和构造参数 UP_DIAGNOSTICS_GATEWAY_MESSAGE("up_diagnostics_gateway_message", "网关诊断上报")
    getTopic() "up/+/+/diagnostics/report"
    getMqTopic() "iot-up-diagnostics-gateway-message"
    getMqttQos() MqttQoS.AT_LEAST_ONCE
    getNumPartitions() 1

    收到 CONNACK 后，getTopics(tenantCode) 把模板中的第一个 + 替换为租户编码，加上 $share/iot/ 后批量订阅。IoT 服务启动且 Pulsar 健康检查通过时，主题工厂按枚举中的主题名和分区数创建 Pulsar 主题。

  2. 在 Spring 可扫描的包中实现 MessageListener，将实际发送操作的 Future 返回给 MQTT 处理器。

import java.util.concurrent.CompletableFuture;
import lombok.RequiredArgsConstructor;
import org.apache.pulsar.client.api.MessageId;
import org.laokou.common.core.config.SystemSettingsProperties;
import org.laokou.common.mqtt.client.listener.MessageListener;
import org.laokou.common.mqtt.client.listener.MqttMessage;
import org.laokou.common.mqtt.client.message.MqttMessageType;
import org.laokou.common.mqtt.client.util.PulsarUtils;
import org.apache.pulsar.spring.core.PulsarTemplate;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
final class GatewayDiagnosticsListener implements MessageListener {
    private final SystemSettingsProperties settings;
    private final PulsarTemplate<Object> pulsarTemplate;

    @Override
    public MqttMessageType getMessageType() {
        return MqttMessageType.UP_DIAGNOSTICS_GATEWAY_MESSAGE;
    }

    @Override
    public CompletableFuture<MessageId> onMessage(MqttMessage message) {
        String destination = PulsarUtils.getGatewayTopic(
            settings.getTenantCode(), getMessageType().getMqTopic());
        return pulsarTemplate.sendAsync(destination, message.payload());
    }
}
  1. 参照 MqttMessageHandler 增加 @PulsarListener，监听 persistent://${system-settings.tenant-code}/gateway/iot-up-diagnostics-gateway-message，使用 SchemaType.BYTES 接收 byte[]。若约定诊断内容为 UTF-8 JSON，在此解码并保存；若定义 Fory DTO，则在发送端和 IotConfig 注册相同且未占用的类型编号。监听器转发的只有 payload，消费端需要的 SN、租户或请求 ID 应随载荷发送。
  2. 重新部署后确认 Broker 出现新订阅，用网关向具体 Topic 发布一条 QoS 1 消息，并在诊断消费者核对请求 ID。默认 supports(topic) 根据枚举中的过滤器匹配，处理器只调用第一个命中的监听器，应避免主题模板重叠。对于 QoS 1，平台在监听器的 Future 成功后才回 PUBACK；此时内置转发流程已完成写入 Pulsar，后续业务处理由消费端确认。

# 5. 联调排查

现象 核对位置
会话保存成功，网关上报无反应 保存只测试连接。检查是否已开启会话、Pulsar 开启事件是否被消费，并在 Broker 查看授权的共享订阅和实际发布 Topic。客户端的 SUBACK 成功日志只检查返回列表非空。
下发出现 B_MQTT_SessionNotOpen 或 B_MQTT_ClientNotConnected 前者表示当前实例找不到该会话 ID，检查网关关联和开启事件。后者表示客户端存在但尚未连通或正在重连，查看 CONNACK、凭据和 Broker 连接日志。
Pulsar 有属性消息，Redis 没有新值 检查 Fory 类型编号、二进制载荷及毫秒时间戳。当前设备属性写缓存使用 device:properties:{tenantCode}:{gatewaySn}，同一网关的多个设备会写同一键；按设备存储时需同步调整写入和查询的键。
长时间无法重连 可恢复的断线按 5、10、15 秒递增延迟，最高 100 秒。认证失败、无权限等被列为致命错误的 CONNACK 会停止自动重连，修正配置后重新开启会话。
发送后掉线，重连后没有收到旧指令 出站 QoS 1/2 的待确认记录仅在内存中，断线会暂停重发计时。当前成功重连分支只重新订阅，未调用 retransmitInflight()。需要可靠补发的业务应持久化指令，并用 requestId 关联回复和去重。

# 6. 用 Go 网关做双向联调

gateway-demo Github开源项目地址 (opens new window)

本节将前文的网关 GW001 换成 Go 示例里的 KEG10000，下挂一台设备 CNC100（数控机床）。联调完成后，平台应能读到机床转速和网关 CPU 使用率，并能按原 requestId 查到读取指令的网关回复。

# 6.1 对齐 Broker、身份和权限

项目 Go 网关 平台侧核对
Broker 同机使用 Compose 时填 tcp://127.0.0.1:41883，独立网关填 tcp://<宿主机可达IP>:41883 doc/deploy/docker-compose/docker-compose.yml 中 emqx 映射 41883:1883。会话管理填写从 IoT 服务能访问的 IPv4 和端口，同一容器网络可走 Broker 内部端口 1883。两端最终连接同一 Broker
客户端 示例 Client ID 为 test-001，连接超时 5 秒。每个同时在线的网关使用独立 Client ID Client ID 用于连接，网关 SN 用于业务路由。Broker 的 TCP 监听器需同时接受 Go Paho 使用的 MQTT 3.1.1 和平台的 MQTT 5。Paho Go 客户端说明 (opens new window)
租户与网关 Topic 和消息体都使用 laokouyun、KEG10000 在该租户下开启会话，登记同名 SN 的网关并绑定会话。登记设备 CNC100，关联到此网关，记下两者的数据库 ID
Broker 账号 使用实际分配给网关的账号密码 网关账号获准按下表发布或订阅。平台账号获准订阅对应上行过滤器并发布下行指令

原 Go 示例把连接目标写成 0.0.0.0:41883。部署时使用上表中的可达地址。下面四个 Topic 是从网关端观察到的实际收发方向，三种发布均设置 retain=false。

网关操作 MQTT Topic QoS Fory 类型编号
发布设备属性 up/laokouyun/KEG10000/CNC100/properties/report 0 245
发布网关属性 up/laokouyun/KEG10000/properties/report 0 244
订阅平台指令 down/laokouyun/KEG10000/command 1 246

# 6.2 运行独立的 Go 联调程序

在空目录创建以下两个文件。示例保留原程序的主题、类型编号、上报顺序和 100 秒指令窗口，选取少量属性便于核对。Go 结构体字段与 Java DTO 对应，消息使用 Fory 原始字节。Java 的 DownCommandGatewayMessage 将字段标为 @Nullable，接收端应保留空值语义，尤其是可能为空的 metadata 和设备字段。Fory Go 字段与类型注册 (opens new window)

models.go

package main

type UpReportPropertiesGatewayMessage struct {
    TenantCode, GatewaySn string
    Timestamp, RequestId  int64
    Metadata, Properties  map[string]any
}

type UpReportPropertiesDeviceMessage struct {
    TenantCode, GatewaySn, DeviceSn, DeviceName string
    Timestamp, RequestId int64
    Metadata, Properties map[string]any
}

type DownCommandGatewayMessage struct {
    TenantCode, GatewaySn, DeviceSn, DeviceName, Command *string
    Timestamp, RequestId *int64
    Metadata, Param map[string]any `fory:"nullable"`
}

type UpCommandReplyGatewayMessage struct {
    TenantCode, GatewaySn, DeviceSn, DeviceName, Command, Message string
    Timestamp, RequestId int64
    Metadata, Payload map[string]any
}

main.go

package main

import (
    "fmt"
    "log"
    "os"
    "time"

    "github.com/apache/fory/go/fory"
    mqtt "github.com/eclipse/paho.mqtt.golang"
)

const tenant, gateway, device = "laokouyun", "KEG10000", "CNC100"

func required(name string) string {
    if value := os.Getenv(name); value != "" {
        return value
    }
    log.Fatalf("请设置 %s", name)
    return ""
}

func wait(token mqtt.Token) {
    if !token.WaitTimeout(5 * time.Second) {
        log.Fatal("MQTT 操作超时")
    }
    if err := token.Error(); err != nil {
        log.Fatal(err)
    }
}

func main() {
    f := fory.New(fory.WithXlang(true), fory.WithTrackRef(false))
    for id, model := range map[uint32]any{
        244: UpReportPropertiesGatewayMessage{}, 245: UpReportPropertiesDeviceMessage{},
        246: DownCommandGatewayMessage{}, 247: UpCommandReplyGatewayMessage{},
    } {
        if err := f.RegisterStruct(model, id); err != nil {
            log.Fatal(err)
        }
    }
    opts := mqtt.NewClientOptions().AddBroker(required("MQTT_BROKER")).
        SetClientID(required("MQTT_CLIENT_ID")).SetUsername(required("MQTT_USERNAME")).
        SetPassword(required("MQTT_PASSWORD")).SetConnectTimeout(5 * time.Second)
    client := mqtt.NewClient(opts)
    wait(client.Connect())
    defer client.Disconnect(250)

    up := fmt.Sprintf("up/%s/%s/", tenant, gateway)
    down := fmt.Sprintf("down/%s/%s/command", tenant, gateway)
    commands := make(chan []byte, 8)
    wait(client.Subscribe(down, 1, func(_ mqtt.Client, m mqtt.Message) {
        commands <- append([]byte(nil), m.Payload()...)
    }))
    log.Println("已订阅", down)
    publish := func(topic string, qos byte, model any) {
        data, err := f.Serialize(model)
        if err != nil {
            log.Fatal(err)
        }
        wait(client.Publish(topic, qos, false, data))
        log.Println("已发布", topic)
    }

    publish(up+device+"/properties/report", 0, &UpReportPropertiesDeviceMessage{
        TenantCode: tenant, GatewaySn: gateway, DeviceSn: device, DeviceName: "数控机床",
        Timestamp: time.Now().UnixMilli(), RequestId: 100, Metadata: map[string]any{},
        Properties: map[string]any{"spindleSpeed": 4380, "programName": "SHAFT_ROUGHING_V2.NC"},
    })
    time.Sleep(time.Second)
    publish(up+"properties/report", 0, &UpReportPropertiesGatewayMessage{
        TenantCode: tenant, GatewaySn: gateway, Timestamp: time.Now().UnixMilli(),
        RequestId: 101, Metadata: map[string]any{},
        Properties: map[string]any{"cpuUsage": "35.6%", "diskUsage": "60%", "interval": 30},
    })

    deadline := time.After(100 * time.Second)
    for {
        select {
        case <-deadline:
            return
        case data := <-commands:
            var cmd DownCommandGatewayMessage
            if err := f.Unmarshal(data, &cmd); err != nil {
                log.Printf("下行指令解码失败: %v", err)
                continue
            }
            if cmd.RequestId == nil || cmd.Command == nil {
                log.Print("下行指令缺少 requestId 或 command")
                continue
            }
            log.Printf("收到下行指令 command=%s requestId=%d param=%v", *cmd.Command, *cmd.RequestId, cmd.Param)
            reply := UpCommandReplyGatewayMessage{
                TenantCode: tenant, GatewaySn: gateway, Timestamp: time.Now().UnixMilli(),
                RequestId: *cmd.RequestId, Command: *cmd.Command, Metadata: map[string]any{},
                Payload: map[string]any{}, Message: "示例仅支持 read_device_properties",
            }
            if *cmd.Command == "read_device_properties" && cmd.DeviceSn != nil && *cmd.DeviceSn == device {
                reply.DeviceSn, reply.DeviceName = device, "数控机床"
                reply.Message = "OK"
            }
            publish(up+"command/reply", 1, &reply)
        }
    }
}

# 6.3 从平台核对两次上报和一次指令回复

本例已用 Go Fory 1.7.7 与项目的 Java Fory 1.7.8 做过本机 MQTT 报文验证：Java 能解码两次属性上报，Go 能解码 Java 生成的读取指令，Java 能从回复中读回原请求 ID 和 OK。以下步骤用于在实际部署中继续验证 Broker 权限、Pulsar 转发、Redis 缓存和指令记录。

  1. 先验上行。 平台会话已连接并订阅后，启动 Go 程序。终端先输出「已订阅」，随后依次输出设备和网关的「已发布」。设备属性只发一次，约 1 秒后网关属性也只发一次。Properties 中的 interval: 30 是演示数据。重跑程序会生成新的毫秒时间戳。

  2. 查平台收到了什么。 在平台所用的 Redis 执行下列命令。设备的 data 应包含 "spindleSpeed":4380，网关的 data 应包含 "cpuUsage":"35.6%"。当前两种键都使用网关 SN 作为末段。还可用 GET /v1/gateways/{网关ID}/properties 核实网关属性。

    redis-cli HGETALL device:properties:laokouyun:KEG10000
redis-cli HGETALL gateway:properties:laokouyun:KEG10000

  3. 在 Go 程序的 100 秒窗口内下发读取指令。 使用已登录的同租户账号，向 IoT 服务的 POST /v1/gateways/commands/read-device-properties-command 发送以下 JSON。将两个示例数字换为 KEG10000 和 CNC100 的数据库 ID。平台会查表后把对应 SN 写入 MQTT 指令。

    {
  "gatewayId": 123,
  "deviceId": 456,
  "command": "read_device_properties",
  "param": {}
}

  4. 用同一个 ID 验收下行和回程。 网关终端应打印 command=read_device_properties 和本次 requestId，随后发布回复。在平台网关指令列表，或通过 POST /v1/gateways/commands/page 按 gatewayId 查询，找到 id 等于该 requestId 的记录。检查 replyStatus=0、replyMessage="OK" 且已有回复时间。示例回复的 payload 是空对象，表示本次模拟收发完成。对接真实设备时，应在读到设备数据后填写 payload，并按实际执行结果填写 message。

若 Broker 已收到属性但平台没有数据，先查平台会话是否在 QoS 0 上报前完成订阅，再检查 Fory 解码和 Redis 的 timestamp。若属性正常而指令收不到，优先查网关是否还在 100 秒窗口内、指令记录关联的会话和目标 SN 是否正确。若网关打印了解码失败，核对 246 的可空字段、两端 Fory 版本和类型编号。若回包已发布但列表没有更新，核对 247 回复中的原始 requestId。
